Job Search Command Center

A local-first job-search operating system: ingest roles from Greenhouse, Lever and Ashby; normalize and persist them in SQLite; rank/filter them; generate AI briefings; and safely prepare applications for human review.

1. Mental model

Discover → Decide → Apply

The repo is not just a scraper. It closes the loop from external job boards to a durable local record and then to action.

Source of truth
SQLite holds job state, user-managed triage fields, application state and an append-only attempt trail. Re-fetches update board-owned data while preserving user-owned decisions.
Two automation boundaries
Network ingestion is automatic; application filling is deliberately review-oriented. The apply runner stops at READY_FOR_REVIEW and records why a human is needed.

4. State & persistence map

Board-owned state

Company, title, location, description, compensation, board URL, last seen.

User-owned state

Status, priority, fit score/summary, notes, Notion page ID. The store intentionally preserves these on re-fetch.

Application state

Application status/URL, ATS provider, completed fields, resume upload, blockers, notes, human-required reason.

Audit history

5. Key files to read in order

app.py — Streamlit composition root and main dashboard. Read this to see how feed, actions, summaries and UI state are assembled.
jobsearch/fetcher.py — ingestion orchestrator. Registers board adapters, fans out with asyncio.gather, normalizes results, and returns explicit health reports.
jobsearch/boards/{greenhouse,lever,ashby}.py — anti-corruption/adaptor layer around three external ATS shapes.
jobsearch/store.py — persistence boundary. Handles migrations, URL-based upserts, state preservation, application metadata and audit attempts.
jobsearch/ranking/fit.py — deterministic, LLM-free profile/preset scoring. Useful contrast with generative AI features.
jobsearch/services/summary_service.py — provider abstraction and streaming AI briefing path with context budgeting and graceful fallback.
jobsearch/services/pipeline_service.py — centralizes subprocess command construction so dashboard buttons and CLI scripts share an execution path.
jobsearch/apply/runner.py — Playwright application workflow, human-review boundary, screenshots and persistence.
tests/ — broad unit/integration coverage across fetching, persistence, migrations, ranking, UI helpers, summaries, apply logic and smoke E2E.

6. Patterns worth remembering

Adapter pattern

ATS-specific fetchers hide provider differences behind a common result shape.

Repository / Store

JobStore isolates SQLite and protects domain/user state during ingestion.

Functional core

Command builders and ranking functions are pure enough to test without subprocesses, UI or LLM calls.

Graceful degradation

Board failures become reports; AI backend failures become readable UI output; DB failures rollback.

Human-in-the-loop

Browser automation prepares applications and produces review artifacts instead of blindly submitting.

Local-first architecture

SQLite plus optional Ollama means core tracking remains usable without a hosted backend.

8. Test strategy

Persistence

test_store.py, test_migrations.py, dedupe tests verify durable state and schema evolution.

Ingestion

test_fetcher.py and board-description tests exercise adapter/orchestrator behavior.

Decision logic

Ranking, filters, parsing, keyword extraction and search-preference tests cover deterministic business logic.

Automation

ATS, field matching, apply review/runner tests isolate safety-sensitive behavior.

Presentation/services

UI components, summary service, pipeline service, markdown export and Notion sync have targeted tests.

Whole-system check

test_smoke_e2e.py provides a thin integration confidence layer.

Design lesson: the repo is most testable where side effects have been pushed behind boundaries. Pure command construction, ranking and parsing are cheaper to verify than subprocess/browser/network behavior.

Debug ingestion

Start at scripts/run_fetch.py → JobFetcher.fetch_all_boards(). Inspect per-board reports before assuming an empty feed is legitimate. Then verify JobStore.insert_or_update_job().

Debug stale or lost triage state

Inspect the URL identity/upsert path in store.py. User-managed fields are explicitly copied from the existing row before update; this is the invariant to protect.

Debug AI summaries

Check provider resolution, Ollama probe, context budget, and whether the digest contains untriaged roles. The service intentionally avoids feeding the entire database to a local model.

Debug auto-apply

Open the generated review directory first: before/after screenshots and structured results show what the browser detected, filled, skipped, or classified as blocked.

10. Extension seams & refactor opportunities

Add another ATS

Implement a new board adapter, normalize into the shared job shape, register it in JobFetcher.fetchers, then add fixtures/tests.

Replace fit scoring

The ranking layer is isolated enough to swap keyword overlap for embeddings, a learned ranker, or hybrid scoring while retaining deterministic filters.

Background execution

The subprocess service is a clean seam for moving fetch/keyword/apply jobs into a task queue if the Streamlit process becomes a bottleneck.

Provider abstraction

The summary service already has two backends. A formal provider interface could make additional local/cloud models easier to plug in and benchmark.

Large app.py

The main Streamlit file is substantially larger than most modules. Continued extraction into UI controllers/view-model-like services would reduce coupling and improve navigation.

SQLite concurrency

SQLite is ideal for this single-user local-first system, but heavier concurrent workers or multi-user hosting would eventually motivate a server database and explicit transaction boundaries.

11. Interview talking points

30-second architecture answer

“I built a local-first job-search command center around a layered Python architecture. Async adapters ingest Greenhouse, Lever and Ashby concurrently into a normalized Job model. A SQLite store is the source of truth and preserves user triage state across re-fetches. On top of that I have deterministic fit ranking, an AI briefing service that can switch between Anthropic and local Ollama, and a Playwright apply workflow that fills only confident fields and stops for human review. I separated side-effect boundaries so ranking, command construction, parsing and state transitions are testable independently.”

Tradeoff: local-first vs hosted SaaS

Local-first minimizes cost, keeps candidate/application data private and makes the tool usable offline. The tradeoff is that Streamlit + SQLite assumes a mostly single-user process; a hosted multi-user product would need auth, a server DB, worker queues and stronger concurrency controls.

Tradeoff: deterministic ranking vs LLM ranking

Keyword/preset scoring is cheap, explainable and stable. It misses semantic matches. A hybrid approach can preserve hard filters and explainability while adding embedding similarity or learned ranking for recall.

Safety story

The apply agent is intentionally not “fire and forget.” It classifies blockers, uses confidence-based field matching, records skipped fields, captures screenshots, persists an audit trail and requires final human approval. That makes failures inspectable and limits automation risk.

What I would build next

Add telemetry around fetch latency/failure rates, ranking quality and application field-match precision; benchmark deterministic vs embedding/hybrid ranking; move long-running tasks behind a queue; and formalize provider/ATS interfaces.
